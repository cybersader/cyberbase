You're hitting on a real gap. Most AI governance frameworks are still focused on model deployment and chatbot usage, while AI coding assistants represent a fundamentally different risk surface — they have deep access to codebases, secrets, environment variables, and can execute commands. Here's how I'd think about this architecturally, keeping costs reasonable by building on identity and data governance foundations you likely already have.

## The Core Problem

84% of developers are using or plan to use AI tools in their workflows, and nearly 70% of organizations estimated more than 40% of their code was AI-generated in 2024. But the governance layer hasn't kept pace. In an Anagram 2025 workplace security survey, 58% of employees admitted pasting sensitive data into LLMs, even when their companies hadn't defined what was allowed. The coding assistant space is even worse because these tools silently read far more context than people realize.

## Architecture Approach: Build on What You Have

**1. Data Classification as Your Foundation**

Before buying anything new, align with existing data governance practices by integrating your data classification (public, internal, confidential, secret) into AI assistant usage policies, ensuring assistants only access data permitted by those classification rules. If you already have data classification in your DLP or identity governance stack, extend those policies to cover what gets fed into AI coding tools. This is free — it's policy work.

**2. Identity-Aware Policy Enforcement**

This is where you tie AI coding governance back to IAM. Connect governance tools with IAM, SIEM, and data classification platforms from day one to avoid silos. The architecture pattern looks like:

- Your existing IdP (Entra ID, Okta, etc.) defines roles and attributes
- Those roles map to what AI tools can access and what developers can do with AI-generated output
- Audit trails tie AI-generated code back to the developer identity

**3. Cost-Effective Tooling Tiers**

For the "don't drop big bucks" constraint, here's a tiered approach:

**Tier 1 — Policy + Process (Near Zero Cost):**
- Write an explicit acceptable use policy for AI coding tools. Define approved use cases — allow AI assistants for boilerplate, documentation, and test scaffolding, but disallow use in core cryptography, authentication flows, or credential handling.
- Ensure AI-generated code is clearly identifiable and mandate peer reviews, establishing thresholds for when reviews are required (e.g., all AI-generated code touching sensitive systems or business logic).
- GitHub has published a [sample policy for internal developer use of AI tools](https://resources.github.com/learn/pathways/copilot/essentials/empower-developers-with-ai-policy-and-governance/) that's a solid starting point.

**Tier 2 — Self-Hosted / Open Source Options (Low Cost):**
- Tabby is a self-hosted AI coding assistant designed for teams that cannot send code to external servers — it runs entirely on your infrastructure and includes team management, usage analytics, and SSO integration. This gives you control over what data the model ever sees.
- Continue is model-agnostic, letting you connect to any LLM (local or cloud), so teams can start with cloud models and migrate to self-hosted options as needs evolve.
- For policy-as-code, Oso is an open-source framework that enables granular authorization in AI and non-AI applications, supporting RBAC, ReBAC, and custom models.

**Tier 3 — Targeted Commercial Tools (Moderate Cost):**
- **Knostic / Kirin**: Kirin integrates directly into coding assistants like GitHub Copilot, Cursor, and Claude Code, detecting vulnerable or malicious libraries, blocking unsafe MCP servers, extensions, and plugins, and surfacing issues directly in the developer's environment. Their approach is specifically identity-connected — ensuring AI workflows are included in existing security controls like logging, identity governance, and incident response.
- **Endor Labs**: Specializes in software supply chain security for AI-generated code, with reachability analysis to identify which vulnerabilities actually pose a risk, and an API-first policy engine. They have a tiered pricing model including a Core plan that's more accessible.

**4. CI/CD Integration as the Enforcement Point**

Integrate policy-as-code frameworks into your AI infrastructure so policies automatically validate model behavior, enforce data provenance rules, and trigger as part of CI/CD pipelines — models or code failing checks get blocked from deployment. This is where governance becomes real enforcement rather than just documentation, and it plugs into tooling you probably already run (GitHub Actions, GitLab CI, etc.).

## The Identity Thread That Ties It Together

The key architectural insight is that legacy IAM platforms like Okta, SailPoint, and IBM offer strong identity governance but lack direct AI-context policy enforcement. You need a thin layer between your identity stack and the AI tools that translates "who is this developer" and "what data are they authorized to access" into "what can this AI assistant do on their behalf." That's the gap tools like Knostic are specifically trying to fill, and it's also something you can partially DIY with repository-level access controls, pre-commit hooks, and secret scanning.

The bottom line: start with policy and classification (free), layer in self-hosted alternatives or CI/CD enforcement (low cost), and only reach for commercial AI governance tools for the specific gaps your identity/data governance stack can't cover natively. The foundation is identity + data classification — everything else is enforcement mechanisms on top.

Okay, now I'm tracking exactly what you're after — the inline enforcement layer that actually connects your identity stack and data governance to the AI coding tool at prompt-time. Honest answer: **this specific integrated product barely exists yet**, and what does exist is fragmented. Here's the real landscape.

## What You're Describing vs. What Actually Exists

The architecture you want looks like:

**Developer identity (Okta/Entra/SailPoint)** → **Policy decision point** → **Prompt interception + DLP/classification enforcement** → **Claude Code / Copilot**

That full chain, purpose-built and integrated? Nobody has it end-to-end at a reasonable price point. But there are pieces that get you close, and they fall into a few categories.

## The Closest Players

**Knostic (Kirin)** is probably the nearest match to what you're describing for the coding assistant layer specifically. Kirin integrates directly into coding assistants like GitHub Copilot, Cursor, and Claude Code, validating MCP servers, scanning dependencies, and enforcing secure policies in real time. They also explicitly work on the identity governance integration side, ensuring AI workflows tie into existing logging, identity governance, and incident response controls. Their approach to RBAC is attribute-based at the knowledge layer — enforcing need-to-know policies at inference time, not just at data access, with pre-deployment simulation and sandbox prompt tracing to detect oversharing paths. The catch: they're still building out direct connector depth to SailPoint/Okta specifically for the coding assistant use case. It's more mature on the M365 Copilot side.

**Prompt Security** is the other major player in this inline interception space. They support a range of AI coding assistants beyond just Copilot — including Codeium, Tabnine, Amazon Q Developer, GitLab Duo, and others — enabling proactive monitoring of AI usage and policy enforcement throughout development cycles. They function as an AI firewall/proxy that inspects prompts and responses. Their integration story leans more toward DLP and data classification than deep IdP federation, but they're closer to the "intercept and apply policy" pattern you need.

**Harmonic Security** takes a different angle that's worth considering. Their MCP Gateway intercepts all MCP traffic, enabling security teams to discover what clients and servers are in use, enforce granular policies to block risky actions, and apply sensitive data models to prevent exfiltration of IP and sensitive information. Their research is also eye-opening for scoping the problem: coding assistants like GitHub Copilot and Cursor generate a disproportionate concentration of access key exposures — 5.7% of all access key exposures despite only 0.4% of usage, a 14× concentration factor.

## The Microsoft Stack (If You're Already There)

If you're in the Microsoft ecosystem, the closest thing to a native integrated solution is the **Purview DSPM for AI + Entra + Endpoint DLP** combination. Purview Endpoint DLP can be configured to warn or block users from sharing sensitive information with third-party generative AI sites, using deep content inspection and contextual analysis. It ties to Entra identity natively, and uses Adaptive Protection to give block-with-override to elevated risky users attempting to paste or upload sensitive information to AI apps in Edge, Chrome, and Firefox. The limitation: this works at the browser/endpoint level. It catches a developer pasting code into a web-based AI tool, but it **does not sit inline with Claude Code's terminal-based workflow or Copilot's IDE integration** in the way you're envisioning. It's more of a perimeter control than a true inline proxy for coding assistants.

## The Honest Gap

Here's the core problem: Claude Code operates in a terminal. GitHub Copilot operates as an IDE extension making API calls. Neither of these tools routes through a traditional web proxy or browser-based DLP in a way that makes it easy to drop an interception layer in front of them. The interception points are:

1. **Network proxy / API gateway** — Route all API calls from the coding assistant through a corporate proxy that inspects payloads. Companies often route Claude Code's traffic through a corporate proxy or LLM gateway service that enforces network policies and logs requests, ensuring data flows only through approved paths. You can do this with environment variables (`HTTPS_PROXY`), but then you need something smart on the proxy side that understands prompt content, not just URLs.

2. **IDE-level enforcement** — Claude Code now supports Enterprise Managed Policies, allowing central administrators to enforce organization-wide rules that cannot be overridden by individual users, with enterprise policies always taking precedence over user settings. GitHub Copilot has content exclusions and its own proxy layer. But these are per-tool controls, not a unified governance plane.

3. **CI/CD as the backstop** — Enforce at merge/build time rather than prompt-time. This is where Endor Labs and traditional SAST/SCA tools pick up what prompt-time enforcement misses.

## What I'd Actually Recommend Building

Given your constraint of not dropping big bucks, the pragmatic architecture today is:

**Layer 1: Identity → Tool Access** — Use your existing Okta/Entra to control who even gets a Claude Code or Copilot seat. SCIM provisioning, conditional access policies, group-based entitlements. This is free with what you already have.

**Layer 2: Proxy-Based Prompt Interception** — Deploy an AI gateway (Knostic Kirin, Prompt Security, or even an open-source option like a custom LiteLLM proxy with policy hooks) that sits between the developer and the AI API. Configure coding assistants to route through it. This is where you bind the identity context (who is this developer, what's their role) to the prompt content (what are they sending to the AI).

**Layer 3: Data Classification Enforcement** — Connect your Purview sensitivity labels or DLP policies to the proxy layer so it can make decisions like "this developer is in the Finance group, this prompt contains data classified as Confidential, block it." This integration is the weakest link in the market right now — most tools can do basic PII/credential detection but few can consume your *existing* Purview classification taxonomy dynamically.

**Layer 4: Audit + CI/CD Backstop** — Log everything at the proxy, feed it to your SIEM, and enforce at build time for anything that slips through.

The uncomfortable truth is that the product you're asking about — the thing that natively federates Okta/SailPoint identity, consumes Purview data classifications, and sits inline with Claude Code and Copilot to enforce RBAC on AI capabilities — doesn't fully exist as a single product yet. Knostic and Prompt Security are the closest, and both are actively building toward it. The market is maybe 12-18 months from having this be a mature, integrated capability. In the meantime, you're assembling it from the pieces above.

package ai.authz

default allow = false

allow {
    input.classification == "public"
    valid_user(input.identity)
}
